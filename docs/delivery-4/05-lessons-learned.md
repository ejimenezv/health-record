# 05 — Lessons Learned

Each entry: the lesson, the *why* (what made it visible in this project),
and how to apply it in the next one. Seven entries, all rooted in
something that actually happened in this codebase or its load test.

| # | Category | Lesson | Why this surfaced here | Future application |
|---|---|---|---|---|
| 1 | **Resource lifecycle in long-lived connections** | If you register a resource (a connection slot, a file handle, a lock), the cleanup must live in the same `try/finally` scope as the registration — not below it. | The WebSocket handler at [`streaming.py:71`](../../ai-service/src/api/websocket/streaming.py#L71) registers the slot, then constructs heavy components (`StreamProcessor`, diarizer, extractor, coordinator) *outside* the `try` whose `finally` releases the slot. A failure in `silero_vad`/`torchaudio` import leaks the slot on every connect, blocking every reconnect with WS code `4002`. | Bracket registration and cleanup in the same scope. Code review checklist: "for every `register/connect/acquire`, where is the matching `unregister/disconnect/release` and is it reachable from every failure path between them?" |
| 2 | **Load-test the realtime path in week 1, not the last week** | Race conditions in connection-construction code only surface under concurrent connect/disconnect storms. Unit tests and single-session integration tests will not find them. | OI-1 was discovered the week before delivery, on the first realistic Locust-driven WebSocket run. Earlier load testing would have revealed it before architecture decisions hardened. | For any project with WebSocket / SSE / streaming: stand up a smoke load test (3 sessions, 10 s) in the same sprint that the streaming handler is written. Run it on every PR that touches the connection lifecycle. |
| 3 | **Rate limits need workload calibration, not defaults** | `/api/v1/query` returns 88% failures (44× HTTP 429, 30× HTTP 500) at 10 concurrent VUs because the `slowapi` config was set with a single-tenant assumption. | Documented in the [load test §4 + §B](../../ai-service/reports/2026-04-30/load_test_report.md). The target NFR is 50 queries/sec; the limiter rejects most traffic well below that. | For any rate-limited endpoint: derive the limit from the published NFR, not from a copy-paste default. Add a load-test job to CI that asserts `< X% rejection at Y RPS` for the documented target throughput. |
| 4 | **Health checks must not call paid external APIs** | `/health` issues a live OpenAI roundtrip on every probe (median 570 ms) — fine for a manual check, expensive when an AWS load balancer probes it every 5 s and an uptime checker hits it every 30 s. | Discovered in [load test §C](../../ai-service/reports/2026-04-30/load_test_report.md). Estimated waste at LB-default probe interval: ~17K extra OpenAI calls per day. | Split into `/health` (cached, in-process state) and `/health/deep` (live external probes). Probes hit the cached one; the deep one runs on a 60–120 s background timer or by manual request. |
| 5 | **Cost tracking is a first-class concern, not a dashboard added at the end** | The `CostTracker` was wired in early; the BSG RF-018 endpoint at `/api/v1/costs` is a thin projection of an already-correct ledger rather than a parallel accounting system. The budget circuit breaker that prevents runaway spend works because the ledger was complete from day one. | Visible in [`cost_tracker.py`](../../ai-service/src/services/cost_tracker.py) and [`cost_dashboard.py`](../../ai-service/src/services/cost_dashboard.py). | For any project that calls paid APIs: instrument the call site, not the dashboard. Define `MONTHLY_BUDGET_USD` on day one, set warning at 80% and critical at 90%, and gate the LLM tier selection on the dashboard's status. |
| 6 | **RAGAS measures more than accuracy; it measures fixture honesty** | `test_diagnosis_quality` failed with faithfulness 0.500 not because the RAG pipeline is bad, but because the synthetic fixture answers cite facts the synthetic contexts don't include. RAGAS correctly penalised the unsupported claims. | [RAGAS run summary](../../ai-service/reports/ragas_run_summary.md) — the fix is to tighten the fixture answers, not change retrieval thresholds. | Apply RAGAS to fixtures the same way you'd apply linting to code: a failure is a signal to investigate, not a number to suppress. Curate the eval dataset with the same care as production data. |
| 7 | **PII separation is an architecture decision, not a refactor** | PostgreSQL for patient metadata + ChromaDB for the medical knowledge base means GDPR/LOPD "right to be forgotten" is a single targeted DELETE on the metadata store. A unified store would have made it a cross-cutting migration. | Documented in [ADR-002](../adr/ADR-002-vector-store-selection.md) and the data-flow design in [`docs/delivery-2/02-data-flow-design.md`](../delivery-2/02-data-flow-design.md). | Any project that handles PII: separate PII from non-PII stores at the architecture stage. Document the retention policy per store. Make the deletion path runnable in dev as a fixture, so it's exercised before the first real subject access request lands. |
